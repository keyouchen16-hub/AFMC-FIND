# 0.8.11 下载链路改进（历史发布，已由0.8.12替换）

最终安装版搜索458条，后台有1条成功解码并置顶，但真实点击该项时重新建会话，60秒内失败。见 `evidence/v0811/installed-search.json` 和 `installed-movie.json`。这暴露了后台成功后冷启动的交接缺陷，0.8.12已修正会话所有权与缓存交接；电影公网起播仍未通过。以下保留本版测试记录，旧“进行中”描述不代表当前状态。

目标：减少有供种资源在校验分片和播放器读取之间的等待，保持实际解码证据排序；不能把外部资源的存在或供种数量当成可播保证。

## 实现

- 默认 BT 下载层改为应用自有 libtorrent 2.0.15 进程，WPF/LibVLC 界面与个人配置保留。嵌入式 Python 3.12.10 和原生组件约 32 MiB，无需用户安装 Python。
- 随机令牌鉴权、仅 127.0.0.1 接口、路径验证、范围上限、只读完整校验分片；短读取立即返回，避免为了凑满读取长度而等待下一片。读取位置和长度同时校验。
- 单节点用普通顺序预读，多节点使用三个连续紧急分片；预读最多约 4 MiB 加分片边界。只在跳转或模式变化时清理紧急队列。失败的强制暂停/重连方案已移除，不保留无限重试。
- MKV 使用 VLC 内置 avformat 解复用。实际进展可续接候选等待，但整组 60 秒硬预算保持；超时有结果，未解码不进入“已验证可播”层。
- 试播过程每两秒报告资源节点数、接收量、速度和校验/解码阶段。没有“必须下载 30% 才播放”的门槛。
- 公开内置来源缺 tracker 时才补公开入口；未知/私人来源不追加。运行库固定摘要和许可检查加入构建、打包、安装前检查。

- 安装版直链/磁力、暂停/停止、双击全屏及恢复、关闭后清理缓存通过；连续三次关闭播放器保留同一主进程。截图前台激活被 Windows 拒绝，未声称安装版可见截图通过。真实搜索状态验收进行中。

## 未解决与边界

真实“蜘蛛侠”搜索返回 311 条，限时检测选出的 12 个候选，三分钟预算内未得到成功解码；最后部分候选因总预算而取消。两条原电影哈希的 60 秒测试同样未通过。不能因此断言永久死种，也不能说本次已解决这些电影播放问题。首帧证据不保证整片持续流畅，公网供种、码率、网络和文件内容仍影响结果。

测试中发现，反复清空限时分片会触发 libtorrent 取消普通队列；多节点滚动队列改善公网样片，但受控单节点仍停顿，最终对单节点保留顺序读取。相关源码依据：https://github.com/arvidn/libtorrent/blob/v2.0.15/src/torrent.cpp#L4932 。所有中间失败日志保留，以当前最终调度日志作为候选验收依据。
