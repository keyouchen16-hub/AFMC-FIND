## 发现与实现

这份MP4头部moov长5,889,150字节，视频数据起于5,889,190，跨3个2,801,664字节种子分片。原初始预取512KiB实际仅一片；多片同时紧迫deadline与滚动优先级并用，实测持续缺少当前片。候选1仍有约56秒停顿，拒绝部署。

采用候选2：初始8MiB/持续16MiB有界窗口，当前片优先级7、下一片6、其余1，取消time-critical deadline路径，按整片量化窗口避免每次128KiB读重排。仍只向解码器交付通过哈希的分片；选中前无payload、文件边界和会话取消规则不变。

发现重试：路由节点>=8时最早5秒，否则20秒；每次实际发送后至少间隔20秒，总数仍最多4次，得到metadata即停止。修正原调度延迟后可能短时间补发多次的情况。未增加额外公共Tracker、未落盘节点缓存、未改系统网络策略。

参考原理仅作分析：libtorrent streaming.html说明两类队列算法及顺序模式/紧迫模式各自取舍；VLC3 imem-access.c回调访问PTS_DELAY固定默认值，因此未靠改file-caching数字假装改善。实际采纳以本次测量为准。
