## AFMC 发现的问题与候选修改

原生 LibtorrentSession 每个资源启动独立 Worker，结束后 DHT 路由节点全部丢弃；已有 MonoTorrent 内存缓存未覆盖原生路径。

候选只在应用进程内缓存最多 256 个公开 DHT 端点，30 分钟过期；每 10 秒从库导出端点快照，经已有鉴权回环状态通道传给父进程。下一 Worker 仅加载端点，不加载节点身份、资源对端、元数据、视频缓存或完整引擎状态。维持隔离 Worker、私有种子规则、所有分片校验及有界发现重试。关闭程序清空，不写个人配置。

API 依据：https://www.libtorrent.org/reference-Session.html 。实际运行接口按本地 Python 绑定验证。

第二候选另加入同资源有效对端缓存：仅验证为公开种子的实际传输过 payload 的公开端点；按完全相同磁力字符串的 SHA256 键隔离，最多 16 个资源，每资源 64 个端点，5 分钟失效；种子文件路径不复用，私有或未知元数据不导出。只导出端点，不导出下载内容或身份。Native 握手仍校验 infohash，upload_mode 保持到安全检查和视频选择之后。候选1与候选2分开运行、分开保留数据。

- 旧 0.8.20 基线与候选串行；迅雷退出后开始；不注入 qBittorrent 对端，不复用视频文件。

## 进一步定位与拒绝的加急实验

第二组复用2的样本：约40秒 Reading=5,603,328，等待piece=2；约60秒累计接收23MB，piece=2仍缺少数据，直到约95秒才起播。说明瓶颈已进入必需分片等待，而非仍在获取种子信息。没有逐块逐对端日志，不把慢节点、片块稀缺、重复请求三种解释中的某一种说成唯一根因。

libtorrent 官方解释顺序下载可能把当前必需数据交给慢peer，让快peer先取后面的块，time-critical机制也可能因重复下载浪费带宽：https://www.libtorrent.org/streaming.html 。因此试验只对阻塞满8秒的当前分片设置一次deadline，完成/取消/超时时复位；没有整个预读窗口反复设置deadline。

## 结论与下一步

1. 迅雷同hash历史任务确实取得约28.7MB/s平均下载量；其内部P2p渠道占99.46%，不支持将此次高速直接归因于会员/离线下载。
2. AFMC重建发现入口/丢弃同资源对端是已定位的实现差距；缓存使这次重复测试的元数据约3秒到达。但无法据此宣称与迅雷拥有相同的资源供给池。
3. 仍未达到用户要求的快速起播和稳定播放，不发布0.8.21、不覆盖安装。公网未受控、同资源有限轮次、headless解码/时钟而非持续可见画面与音频；本轮没有宣称完整影片流畅。
4. 下一步需要采样阻塞片块的可用对端、已分配请求与实际到达时间，区分供给稀缺和队列拖延。只在有这些证据后再调整调度，不继续堆节点/扩大缓存/反复加急。迅雷内部P2P与标准BT的逐连接对应仍未知，不自动引入商业SDK、云盘或账户凭据。
