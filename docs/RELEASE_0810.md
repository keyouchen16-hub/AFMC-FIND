# AFMC FIND 0.8.10 — 可播排序纠正与真实资源诊断

## 已修正

综合推荐改为严格证据分层：已验证可播 → 已校验数据、播放未确认 → 未验证 → 本次超时/失败；层内按相关度排序。失败资源即使相关度极高也不能越过前面的层。显式大小、时间等排序保持用户选择。结果数下显示已验证数量；零成功明确显示“暂无已验证可播资源”。过期成功退回未知。

后台预算最多 12 个候选、两个并发、三分钟总预算；一批失败继续后续批次，达到三个成功可结束。用片名/年份线索轮流取不同作品，再取其余版本，调度时忽略方括号内发布标签和大小冲突；此调度分组不用于播放替换，播放替换仍使用原严格身份规则。单次原始等待 25 秒，已有校验数据时给予一次 30 秒解码延长，仍受整组/全局预算约束。正式播放前取消后台检测。

试播成功条件加强为至少十个视频解码帧且播放时钟达到一秒，而非单帧到达；这仍仅表示近期起播，不保证整部影片或完整下载。探测使用单独的 VLC dummy 视频/音频输出实例，避免后台探测开原生窗口或发声。

磁力带 tracker 时也进行独立 DHT 引导，避免 tracker 不可达便跳过备用引导。候选间在内存中复用最多 256 个路由节点，30 分钟过期；没有修改防火墙、端口映射、代理或系统设置。仍由 MonoTorrent 决定各 torrent 是否允许 DHT。

## 真实测试与未解决边界

使用现有来源配置只读搜索“蜘蛛侠”，首轮得到 311 个结果（每源一页，与界面三页数量不同）。12 候选中 11 次限时失败，最后一项由三分钟总预算停止，无可播成功。后续中文/英文片名对照与节点数据保存在 evidence/v0810。部分资源只有路由节点/资源连接但视频数据 0 字节；有条目拿到元数据进入 Downloading，仍然 0 字节。不能据此宣称永久死种，也不能说用户实际电影播放问题已解决。

使用 WebTorrent 官方公开测试片 Sintel 对照，确实连接公网节点、收到约 1.77 MB、进度约 1.4% 时成功解码，证据 public-control.log。这说明不是所有公网 BT 都失败，但不能替代相同电影 hash 在其他下载客户端的对照。用户明确表示尚未做其他客户端对照。

官方测试片来源：https://webtorrent.io/free-torrents ，https://webtorrent.io/intro 。未把来源声明的做种数当作实测成功，也未将本地样片测试冒充真实电影可播。

额外在隔离 Python 虚拟环境使用 libtorrent 2.0.15 比较三个相同电影 infohash：崭新之日、2002 蜘蛛侠、No Way Home。两分钟 DHT-only 比较均为零数据；加入官方 Sintel .torrent 正对照后，再运行两分钟，测试片收到 3,915,776 字节、两个种子，三部电影仍零数据。比较电影时没有附加原 tracker 列表，因此只说明该条件下仍未收到数据，不是完整客户端等条件比较，也不是永久死种结论。证据 independent-engine.json / independent-control.json，缓存清理成功。

安装版复查发现检测开始时状态尚未立即更新，已补 RefreshResults；安装版验收脚本现在必须观察到“检测中”再等待其消失，防止在搜索结束、探测刚启动时提前宣布完成。

13:22 的安装版完整流程发生原生异常退出，验收未通过。Windows 事件与 minidump 表明执行位置为已卸载 D3D11.DLL+0x5f215，异常 C0000005；转储未提供可归因到具体源码的完整调用栈，不能归咎系统驱动。已保存 installed-crash.txt、crash-stack*.txt，并对探测 LibVLC 设置 avcodec-hw=none，同时将每个探测 MediaPlayer.EnableHardwareDecoding=false（仅无画面后台/候选试播，正常观看设置不变）。随后重跑播放回归和安装版相同交互流程；最终复测结论见 PROJECT_STATE。测试脚本增加进程退出立即失败及覆盖旧报告，禁止使用上轮成功报告掩盖本次失败。
