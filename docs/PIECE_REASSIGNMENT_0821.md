# 迟到分片重新分配实验（2026-11-06/07，未发布）

负责人 Codex。用户要求继续使用磁力 `2EE672984434179AA8A7C5D2EBD0A94B38EB2960`，同时改善真实起播和卡顿之后再安装。安装版仍 0.8.20；本记录的夹具、原生库和候选不构成发布验收。

## 已确认的机制

- 官方 libtorrent 2.0.15 的 piece_priority 0→7 不取消已发出的请求。
- 新的时间关键集合触发 cancel_non_critical，但占位片已完成时不会触发；首次试验用已完成占位片无效，已改为断言占位片未完成。
- 受控真实 BT 协议夹具捕获慢节点 block0 于 3.02 秒收到 CANCEL，却于 3.31 秒重新获得相同块；快节点 5.64 秒收到该块请求，6.92 秒发送。仅释放不足以保证转交。
- 受控 baseline 7.594 秒完成首个 128 KiB 校验读取，priority-reset 同为 7.594 秒；修正后的 cancel-reassign 7.062 秒。夹具是合成字节，不能称为电影起播性能。
- 第一次无效 cancel-reassign 的结果文件被第二次同名文件覆盖；该失败只保留终端记录（5.937 秒、没有 CANCEL）。已改成每次 UUID 文件，避免证据覆盖。
- 上游 `set_peer_download_limit` 兼容 API 实现为空，不能作为有效限速或降低分配权重的依据。

## 独立原生实验

源码固定 v2.0.15；try_signal 固定 105cce59972f925a33aa6b1c3109e4cd3caf583d。Boost 1.87.0 zip SHA256 校验通过：f367a218d27b23b568956bacf56d08d2c1d9647211337136be8cac5cb2ff0828。

Python 开发文件为官方 NuGet 3.12.10；OpenSSL 使用 CPython 3.12.10 官方依赖 openssl-bin-3.0.16.2，commit 1174fd43d858425c345b16d631716fb98ba492ea。保留 HTTPS、BT 加密、DHT、流式支持；使用已有 VS2022 BuildTools，未安装系统工具。

`scripts/Patch-NativePieceRetry.py` 生成有上游备份的窄补丁。`Build-NativeStreamCandidate.ps1` 构建于 `.tools/native-stream-build`；没有改原运行库。初始候选仅考虑停滞 8 秒且仍缺 >=8 KiB 的当前读取块。后续版本与实际测试结论如下，不把初版阈值视为最终策略。

## 验收要求

1. 真正 BT wire 请求转交、SHA1 正确、连接保留；快节点中途掉线仍有恢复路径。
2. 同磁力全新载荷缓存、基线与候选串行测试；元数据/首次解码/后 120 秒停滞分开。
3. 记录连续可读校验字节和阻塞片实际供给，不把总下载速度当可播放速度。
4. 真实 WPF 与必要回归完成，重复测量有改善后才发布安装；无改善则保留 0.8.20。

## 首轮实现与测量

原生构建成功，启用 HTTPS、加密和 streaming。首次静态 Boost Python 链接声明缺失导致 LNK1120，补充 BOOST_PYTHON_STATIC_LIB 后成功；上游绑定仍有 C4267/C4456 等警告，不能称为零警告构建。

取消实验在替代节点掉线时出现同刻重新分配给原节点的行为，改为原生 `time_critical | busy` 有限备用副本，暂时保留原请求。完整块到达后由 libtorrent 处理其余副本；不保证原请求保留到整片哈希通过。原生 SHA1 校验仍是向解码器供数的前置条件。

## 第二轮策略与恢复边界

按块进度估算持续供数，等待至少 8 秒、剩余至少 512 字节、实测块速率低于 4 KiB/s、预计剩余超过 4 秒才选择救援；备用连接须持有该片、未被 choke，且有超过 16 KiB/s 与阻塞块三倍速率的证据。空闲连接可参考 30 秒内实际增加载荷时的速率，端点重新连接的计数回退会清除旧证据。每分钟最多 8 次成功救援，每次最多 4 块，每块最多一个 AFMC 额外副本。原生仍在每块请求前检查连接资格，不取消原请求。

原生候选 v2 SHA256：`EDFB6E466C77B0907CF29D257F590B37014B7CED5B002D6BEA83C2F73A5B8238`。16 项 Python 策略条件检查通过。

以上是后台真实解码及播放时钟的采样结果，停顿定义为起播后约一秒采样中时钟推进不超过20ms；不是人眼/音频验收或全片保证。公网供给随轮次波动，不能把更快起播或更差停顿全部归因于策略。当前**未通过稳定同时改善起播和卡顿的门槛**，不升级、不安装，不继续扩大参数试错。

下一步保留的明确限制：Python选中慢连接后原生仍遍历该连接的目标片请求，尚未精确指定最老的block；原生空闲快连接参考历史峰值与最近收片时间，不等同于严格30秒窗口的供给速率；分片等待、解码器预读和可持续缓存需继续对齐。候选组件摘要清单、真实WPF及发布回归也尚未验收，不能直接打包当前隔离目录。
